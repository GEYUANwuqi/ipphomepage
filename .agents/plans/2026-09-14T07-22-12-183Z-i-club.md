## 一、插画色与界面色分离

### 已定位的问题

`src/theme/palette.ts` 中，绿/杏装饰色复用了随昼夜改变的 `primaryContainer / onPrimaryContainer`；`i` 使用单独的 `--art-primary`。因此三张插画卡片的昼夜变化不一致。严格说，`i` 也有 tone 80→70 的轻微变化，并非完全不变。

### 推荐改法

建立三类颜色：

1. **界面颜色**：导航、按钮、服务卡片背景、表单、对话框，继续使用完整 M3 动态昼夜角色。
2. **主题协调的插画固定色**：I++ 几何卡片、非文本装饰、书封装饰，使用独立 `--art-*` token。同一 seed 下，其填色、符号颜色、边沿色在昼夜完全一致；换 seed 时可作 HCT 色相协调。优先使用 M3 fixed / fixed-dim 角色及其成对前景，或固定 HCT tone，不再引用随模式变化的 surface/container 角色。
3. **固有素材颜色**：站娘灰紫发色、蓝色眼睛、金色铃铛，人物头像、项目封面、证书图片，不被用户主题色整体重染。

默认恢复偏柔和的紫、薄荷绿、暖杏色组合，避免夜间两个加号变成深色反相块。夜间只调整插画外部阴影/环境衬底，不对图片应用 invert/hue-rotate，也不通过降低整组 opacity 让符号变脏。

服务导航卡片是 UI 容器，仍随夜间模式变化；卡片内部的书本/证书/气泡插画与主体三块几何图形共享明确的插画策略。正式证书不改。

## 二、站娘：识别元素，而不是堆满人物

### 参考图可提取的特征

- 灰紫色头发、明显猫耳与发梢轮廓；
- 蓝色眼睛、金色铃铛、卷曲猫尾；
- 猫爪和 ++ 的组合；
- 两张照片服装配色不同，不能仅据此制定唯一完整服设。

两张 JPG 都是实物拍摄，包含反光、透视、环境背景和裁切，**不用作直接抠图立绘**。不把 Dora SSR 的角色素材当作 IPP 站娘。

### 推荐的三处落点

| 位置 | 表现 | 动效与边界 |
|---|---|---|
| 首页 Hero | 保留 I++ 主构图；在卡片边缘安排一个小型猫耳/爪子探头轮廓，与卷尾弧线构成陪衬 | 停留时一次轻微耳朵/尾巴动作，不自动循环，不追逐鼠标，不遮文字 |
| 成员书架标题区 | 一只简化的 SVG 猫娘探头，像从书架边缘探出；保留灰紫头发、猫耳、蓝眼睛和铃铛 | 只画有限范围的头部/小爪；作为非交互装饰，不把人物伪装成按钮 |
| 页脚/空状态 | 低密度猫爪、铃铛或卷尾线条 | 静态为主；不替换重要功能图标，不在所有卡片重复贴脸 |

不做全屏漂浮宠物、聊天机器人、眼睛持续跟随、随机弹窗，避免干扰阅读与问卷。

### 能力与素材交付边界

可稳定实现：SVG 分层图形、符号系统、简化头部形象、CSS/WAAPI 局部动作和可替换素材接口。

不承诺：从照片无损恢复原画、复刻原作者线稿/完整服设、高质量完整人物立绘或 Live2D 绑定。

实施顺序上先提交一个局部形象预览，确认其“像不像 IPP”后再扩展使用。若效果不佳，退回只有猫耳/卷尾/铃铛的符号方案，而不是以普通猫图冒充官方站娘。后续透明 PNG/WebP/SVG 原画可替换，不影响页面结构。

## 三、信息架构：首页精选，独立页完整展开

推荐路由：

- `/`：品牌介绍、原有三个服务入口、精选项目、精选成员、简短社团共识与页脚；
- `/projects`：项目工坊，完整项目集合；
- `/people`：成员书架，核心成员与支持者；
- `/assessment`、`/verify`、`/admin` 及相关动态路由保留。

首页示意：

```text
品牌导航 + 主题设置
Hero：让好奇心不断加一 / I++ 固定色插画 + 少量猫娘细节
三个服务入口：博客 / Blogroll / 素质问卷
项目工坊：Dora SSR 主展位 + 两个精选小卡 → 全部项目
成员书架：4 位精选成员 + 支持者说明 → 认识大家
压缩后的共识区 / CTA
页脚：官方 GitHub、博客、其他入口 + 少量站娘符号
```

新增内容不只是继续往下堆。压缩现有重复宣言与问卷 CTA，保留清晰节奏；首页不展示全体人员、不展示所有仓库。

导航维持最多五个主目的地：首页、项目、成员、问卷、验真。桌面使用现有页头体系；窄屏若容不下，采用 M3 五项图标+文字导航栏并处理底部安全区，不硬挤超宽横排。管理入口仍在页脚。主导航链接可键盘访问，保留 current 状态和现有转场。

## 四、成员书架：轻量书本隐喻

### 卡片构图

采用 M3 outlined / filled card 作基础，而非真的三维翻书：

- 左侧细书脊：年份与小型索引；
- 主体封面：头像、名称、身份标签；
- 下方简介：默认约 3 行，长简介通过明确的“展开简介”控件或详情对话框查看；
- 右侧书签：相关链接，始终可见而非仅 hover 出现。

桌面 3–4 列、平板 2 列、手机 1 列。书本感来自书脊、浅纸页边和书签，正文不旋转，排版依然清晰。

动效：hover 时封面仅抬起/轻偏转约 2–3°，书签轻轻伸出；鼠标离开回到原位。触屏不依赖 hover，键盘焦点有同等反馈。保留 reduced-motion 降级。

链接不嵌套在整卡 anchor 内；书签自身为独立可聚焦链接。最多显露三个书签，剩余链接用明确的“更多链接”按钮展开 M3 菜单/对话框。点击热区不少于 48px，图标之外必须有名称，不能只靠 tooltip。

没有相关链接时不画假的书签按钮。头像不存在时使用名称首字/抽象图形回退，避免破图；长名称、长简介、多身份文字和很多链接都要有边界测试。

### 分组、筛选与排序

- 顶层区分“核心成员”和“支持者”，身份标签仅展示编辑提供的文字，不用标签推断职位等级。
- 提供名称/简介搜索、组别筛选、年级筛选；人数少时保持轻量，不做复杂分页后台。
- 默认每组按入学年份从新到旧；同届保留 JSON 顺序，不随机排序，也不自动把某类头衔排为更高等级。
- 首页最多选择四位 `featured` 成员，顺序由内容维护者明确控制。支持者有独立入口/分组，不被混同为现任核心成员。
- 本次支持者按用户给定的“个人成员”结构处理，不扩展成企业赞助/金额排行榜。

### 数据契约

推荐 `src/content/people.json`，头像放在 `public/images/people/`。

```json
{
  "people": [
    {
      "id": "demo-001",
      "name": "示例成员",
      "avatar": "/images/people/example.webp",
      "description": "这是一段介绍，说明兴趣、贡献或正在做的事情。",
      "title": "前社长",
      "year": 2025,
      "group": "core",
      "featured": true,
      "links": [
        { "label": "GitHub", "url": "https://github.com/example" },
        { "label": "个人博客", "url": "https://example.com" }
      ]
    }
  ]
}
```

- `name / avatar / description / title`：字符串；`year`：入学年份整数，不用当前年换算。
- `links`：可省略或空数组；每项有显示名称和 URL。
- `id`：稳定唯一标识；`group`：`core | supporter`；`featured` 可选。
- 校验重复 ID、类型、年份边界、本地头像路径和文件是否存在、链接协议。仅允许 http(s) 外链，拒绝 javascript/data URL；内容作为纯文本渲染，不允许 JSON 内注入 HTML。
- 添加正式成员只需要补 JSON 和图片，无需修改 React。开发中热更新；生产通过构建/部署发布，不把静态 JSON 误说成线上自动写入数据库。
- 本次不增加成员编辑后台、不接入账号绑定，也不抓取 GitHub 用户作为真实成员。

### dev mock 策略

- 正式 JSON 初始为空，不添加真实人员。
- dev 中按固定随机种子产生约 10–12 位演示成员，涵盖两组、不同年份、长描述、无链接与多链接等情况；使用本地生成的抽象/SVG 头像，不外链随机人像服务。
- 页面明确显示“开发演示数据，非真实成员”。随机发生于生成过程，不在每次渲染/刷新时改变排序。
- mock 模块和素材放在 `src/dev/`，通过 `import.meta.env.DEV` 隔离；不放进会无条件复制到 dist 的 public 目录。
- 生产构建必须验证 mock 不被打包或渲染。正式数据为空时：首页不显示假成员，`/people` 显示简洁的整理中状态。

   - 基于 Dora SSR、使用 YueScript 的游戏项目；README 中致谢 IppClub 技术支持。
   - 推荐标注“社区协作游戏 / 社团技术支持”，不宣传为当前在校成员独立创作。

Dora-Example 作为“开始创作”的示例入口，不必占用一个与旗舰项目同等权重的展位。

不能把这些仓库统称为停止维护的历史项目。仓库活动也不等于用户可以获得维护承诺，推荐不在首版展示未经确认的“活跃维护”徽章。

### 视觉与内容

- Dora SSR：较宽主展位，使用 16:10 视觉区、简短用途、能力关键词与三条操作入口。
- YueScript / Dora Story：较紧凑工具卡，重点解释“能拿来做什么”。
- LSD：作品卡，强调游戏成果与参与关系，而不是与引擎混为同类。
- `/projects` 用引擎、语言工具、游戏/框架等分类组织。每卡显示简洁摘要、项目性质、对应链接。
- 所有卡片使用 M3 表面和状态层，避免密集堆叠 star、fork、语言占比等开发者仪表盘信息。
- 首版采用本地静态 JSON 维护精选，不运行时调用 GitHub API、不引入 token、不依赖外站响应决定首页能否显示。
- 不展示实时星数、相对更新时间或无依据的维护结论。需要显示维护说明时，必须人工核查并记录核查时间；默认说明“维护情况以仓库为准”。

### 封面素材

不把程序代码 MIT 许可等同于全部美术素材自由使用。Dora / YueScript 自有角色与 IPP 站娘也不能混用。

首版可用原创的代码/关卡/对话窗示意封面，并明确是图形示意，不伪装成真实运行截图。经确认可用于官网展示的项目 logo、截图再本地优化后替换；记录出处与必要授权。未经确认不直接抽取 LSD 美术/音乐资源。

推荐内容路径：`src/content/projects.json`；媒体放在 `public/images/projects/`。包含稳定 id、名称、摘要、项目类别、归属/参与说明、精选标记、可选封面与源码/官网/文档链接；建立与成员数据同级的构建校验。

## 八、验收标准

### 视觉与交互

- 每个预设种子色下，昼夜切换前三张几何装饰的填色/前景保持一致；UI 容器依然正确切换。
- 用户自选颜色不改变角色发色、头像、真实封面与正式证书。
- 320px 起无书签/导航横向溢出；成员卡 1/2/3–4 列布局正确。
- 书签全部可通过触摸与键盘访问；长名字、空链接、多链接、损坏头像和空数据都有合理表现。
- 站娘不遮挡文字、按钮或表单；没有无休止动效；reduced-motion 和现有圆形模式转场保持有效。

### 内容与工程

- 新增一条符合 schema 的成员 JSON 与一张头像后，无需改组件即可展示。
- 无效 JSON、重复 ID、路径越界、缺图、危险链接给出明确的构建/开发错误，而不是悄悄发布破损名录。
- dev demo 具有明确标记；生产构建既不展示演示成员，也不输出 mock 数据/头像资源。
- 项目描述与官方资料匹配，不虚构成员参与、维护状态、活动或许可。
- 保持现有 17 项单元/接口测试和 22 项浏览器回归的通过状态，并新增上述内容驱动、固定插画色、书签交互与生产隔离测试。
